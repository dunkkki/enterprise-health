# 企业健康管理平台 — 错误日志

## 2026-07-28

---

### 1. 数据库表缺少外键约束

**类别**：后端 - 数据库设计

**现象**：建表 SQL 里 COMMENT 写了 "FK→xxx"，但没有真正的 `FOREIGN KEY` 约束。18 张表之间全靠应用层代码维护关系。

**原因**：设计时只画了 ER 图，SQL 里漏写了外键 DDL。

**解决方法**：
- 逐表分析关联关系，补了 23 条 `ALTER TABLE ADD CONSTRAINT ... FOREIGN KEY ... REFERENCES ...`
- 级联策略：CASCADE（用户删→体检记录跟着删）、SET NULL（用户删→操作日志保留但 user_id 置空）、RESTRICT（有结果明细就不能删套餐模板）
- 两个自引用列（`department.parent_id`、`menu.parent_id`）不加 FK，因为根节点用 0 做 sentinel value，不是合法外键值

**你的想法**：


**我的想法**：大部分团队跳过了外键，理由是"性能"或"应用层保证"。但这种项目规模不大，加上外键零开销，换来的是数据库层面的强制一致性。唯一的代价是 INSERT 顺序和 DELETE 级联要理清楚。

### 2. 数据库表缺少 UNIQUE 约束

**类别**：后端 - 数据库设计

**现象**：`user_role`、`role_menu`、`intervention_participant` 三张关联表没有唯一约束，理论上同一个角色可以分配给同一个用户多次。

**原因**：建表时只定义了主键 ID，忘了关联表的标准做法——联合唯一键。

**解决方法**：
- `user_role` 加 `UNIQUE(user_id, role_id)`
- `role_menu` 加 `UNIQUE(role_id, menu_id)`
- `intervention_participant` 加 `UNIQUE(plan_id, user_id)`

**你的想法**：


**我的想法**：这是典型的设计疏忽。中间表的 ID 主键 + 联合唯一键是标准范式，主键保证行标识，唯一键保证业务唯一性。好在这三张表当时没有重复数据，加约束时不需要清理。

### 3. exam_schedule.target_dept_ids 违反 1NF

**类别**：后端 - 数据库设计

**现象**：排期表用 `VARCHAR(512)` 存 JSON 数组 `[2,3,4,5]` 来表示目标部门。无法用 SQL JOIN，不能用 FK 约束，解析靠 Java 代码 `replace("[","").replace("]","").split(",")`。

**原因**：图省事，一个字段搞定多对多关系。

**解决方法**：
- 新建 `schedule_dept(schedule_id, dept_id)` 关联表，联合主键 + 双 FK（CASCADE）
- 迁移历史数据：用 `SUBSTRING_INDEX` 解析 JSON 数组插入新表
- `ExamSchedule` 实体删掉 `targetDeptIds` 字段
- Controller 改收 `ScheduleDTO`（含 `List<Long> targetDeptIds`）
- Service 改读/写 `schedule_dept` 表
- 删掉旧列

**你的想法**：


**我的想法**：JSON 存数组是数据库设计里最常见的偷懒反模式。表面上省了一张关联表，实际上每次查都要 `JSON_CONTAINS` 或应用层 split，连 FK 都建不了。拆成关联表后 JOIN 就能查出部门名称，排期列表接口顺手就返回了 `targetDeptIds: [2,3]`，前端直接用。

### 4. health_risk_result 缺 UNIQUE 约束，设计 1:N 实际 1:1

**类别**：后端 - 数据库设计/前后端不一致

**现象**：`health_risk_result` 表设计成 `record_id` 可重复（一条体检记录可以有多次评估），但代码里 `assess()` 每次先 DELETE 旧结果再 INSERT，实际是 1:1。

**原因**：设计文档写的 1:N，代码实现的是覆盖式重新评估，两者没对齐。

**解决方法**：
- 加 `UNIQUE(record_id)` 约束，从数据库层面保证 1:1
- 代码逻辑不变（DELETE + INSERT），唯一约束当兜底

**你的想法**：


**我的想法**：设计和实现不一致比单纯的 bug 更危险——下一个接手的人看到表结构以为是 1:N，写了个不删旧的 INSERT，直接炸 UNIQUE 约束。现在约束加了，表结构和实际语义一致。

### 5. exam_record 缺少录入人字段

**类别**：后端 - 数据库设计

**现象**：体检结果表明细有 `record_id`、`item_value`、`is_abnormal`，但没有记录是谁录入的。

**原因**：设计时漏了审计字段。

**解决方法**：
- `exam_record` 加 `updated_by BIGINT`，FK → `user.id` ON DELETE SET NULL
- `ExamRecordServiceImpl` 录入结果时 `record.setUpdatedBy(StpUtil.getLoginIdAsLong())`

**你的想法**：


**我的想法**：体检数据是敏感信息，没有录入人追溯在合规审计上是硬伤。哪怕暂时没有审计需求，加一个字段的成本几乎为零。

### 6. 多处业务表缺少 updated_at

**类别**：后端 - 数据库设计

**现象**：18 张表里只有 `user` 有 `updated_at`，其他表都只知道创建时间不知道最后修改时间。

**原因**：建表时没统一加审计字段。

**解决方法**：
- 8 张核心业务表加 `updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
- 关联表、日志表、字典表不加（只增删不改的表不需要）

**你的想法**：


**我的想法**：`ON UPDATE CURRENT_TIMESTAMP` 是 MySQL 原生支持的，不用写任何 Java 代码，数据库自动帮你维护。唯一的成本是每个表多了 8 字节。

### 7. role.code 缺少 UNIQUE 约束

**类别**：后端 - 数据库设计

**原因**：和关联表一样的问题，漏了。

**解决方法**：加 `UNIQUE KEY uk_role_code (code)`

**你的想法**：


**我的想法**：code 是角色的逻辑标识，代码里会 `WHERE code = 'admin'` 来查。如果不唯一，查出来两条 admin 行，逻辑就炸了。

### 8. 日期字段缺少 CHECK 约束

**类别**：后端 - 数据库设计

**现象**：`exam_schedule` 和 `intervention_plan` 的 `end_date` 可以早于 `start_date`。

**原因**：MySQL 8.0 之前不支持 CHECK（语法不报错但被忽略），团队习惯性不写。

**解决方法**：
- `exam_schedule` 加 `CHECK (end_date >= start_date)`
- `intervention_plan` 加 `CHECK (end_date >= start_date)`
- 测试：发了一个 `startDate: "2026-12-01", endDate: "2026-01-01"`，后端 500 拒绝 ✓

**你的想法**：


**我的想法**：MySQL 8.0.16+ 完整支持 CHECK，MariaDB 也支持。现在不用的唯一理由是"兼容老版本"，但这个项目 MySQL 8.0，没理由不用。

### 9. 前端白屏 — localStorage 脏数据崩 JSON.parse

**类别**：前端 - 异常处理

**现象**：打开页面完全白屏，Console 无任何输出。

**原因**：`router/index.js` 的 `beforeEach` 里 `JSON.parse(localStorage.getItem('user'))` — 如果 localStorage 里有损坏的数据（之前异常退出、浏览器写入了非 JSON 字符串、或者值是字符串 `"undefined"`），`JSON.parse` 直接抛异常，整个 Vue 应用初始化失败，`#app` 永远是空的。

**解决方法**：
- `router/index.js`：抽 `getUser()` 函数，try-catch 包裹 `JSON.parse`，过滤 `"undefined"` 字符串
- `stores/user.js`：同样 `safeJSON()` 包裹所有 localStorage 读取
- 加 `/:pathMatch(.*)*` 兜底路由，防止外部脚本注入了不存在的路径也白屏

**你的想法**：


**我的想法**：`JSON.parse` 不加 try-catch 是前端新手最常见的坑之一。localStorage 是浏览器给的，用户、插件、甚至浏览器自己都可能往里写东西，永远不要信任它的内容。

### 10. 图标 tree-shaking 导致生产构建报错

**类别**：前端 - 构建配置

**现象**：开发模式正常，生产构建后报 `Uncaught TypeError: v[w] is not a function`。

**原因**：`MainLayout.vue` 里 `<Fold />`、`<Expand />` 和 `<component :is="dir.icon" />` 依赖全局注册的 Element Plus 图标。`main.js` 里 `import * as ElementPlusIconsVue` 注册了全部图标，但 Vite/Rolldown 生产构建时 tree-shaking 把"看似未使用"的图标剔除了，因为动态字符串 `<component :is="'DataAnalysis'" />` 对静态分析器不可见。

**解决方法**：
- `MainLayout.vue` 显式 `import { Fold, Expand, DataAnalysis, OfficeBuilding, ... }` 9 个图标
- 动态图标改用 `iconMap[dir.icon]` 解析，不再依赖全局注册

**你的想法**：


**我的想法**：`import *` 在开发模式没问题，生产模式的 tree-shaking 行为依赖打包工具的静态分析能力。字符串动态组件引用绕过了分析，最稳妥的方法是显式 import + 映射表。这也是为什么 Element Plus 官方文档建议按需导入图标。

### 11. 点登录没反应 — API 响应层级取错

**类别**：前端 - 异常处理

**现象**：正确账号密码点登录按钮，loading 闪了一下，页面没跳转，也不报错。

**原因**：两个 bug 叠加。
- **Bug A**：`stores/user.js` 的 `login()` 里取了 `res.data.token`，但 API 返回格式是 `{ code:200, data: { token:"..." } }`，少取了一层 `.data`。`token.value` 被赋值为 `undefined`。
- **Bug B**：`login()` 里 `res.data.data` 是 `null` 时 `d.token` 抛 TypeError，但 `Login.vue` 的 `doLogin()` 只有 `try-finally` 没有 `catch`，错误被静默吞掉，用户看不到任何反馈。

结果：登录 API 成功返回 → token 存成 undefined → router 跳到 /dashboard → 路由守卫发现没 user → 重定向回 /login。整个过程不到半秒，用户看起来就是"没反应"。

**解决方法**：
- `stores/user.js`：先检查 `res.data.code !== 200`，失败直接 `throw Error(res.data.msg)`
- `Login.vue`：加 `catch (e) { ElMessage.error(e.message) }`，加表单校验（空值不发请求）

**你的想法**：


**我的想法**：两个小 bug 凑在一起产生了"静默失败"——最坏的失败方式。任何一个单独修复都不够：修了 A 只是 token 不对但无提示，修了 B 只是捕获了异常但没有业务错误信息。这里的教训是：**API 调用的错误处理要同时覆盖 HTTP 异常和业务错误码**，不能只靠 axios 拦截器处理 401。

### 12. 外部脚本路径污染 Vue Router

**类别**：前端 - 路由配置

**现象**：Console 刷屏 `[Vue Router warn]: No match found for location with path "/hybridaction/zybTrackerStatisticsAction?..."`。

**原因**：VSCode 内置浏览器或浏览器插件注入了追踪脚本，在 Vue Router 初始化瞬间向地址栏推了不存在的路径。

**解决方法**：加兜底路由 `{ path: '/:pathMatch(.*)*', redirect: ... }`

**你的想法**：


**我的想法**：这个警告本身不会导致白屏，但暴露了两个问题：(1) 路由没有兜底，任何不认识的路径都渲染空白；(2) 外部环境不可控，只能防御性编程。

### 13. 侧边栏为空 — Jackson Long→String 导致前端严格比较失败

**类别**：前端 - 渲染逻辑

**现象**：admin 登录后侧边栏一片空白，没有任何菜单。

**原因**：后端 `JacksonConfig` 全局把 Long 序列化为 String（防止雪花 ID 精度丢失），菜单的 `parentId` 返回 `"0"`（字符串）。前端 `menuTree` 计算属性里用 `m.parentId === 0` 严格比较，`"0" === 0` 恒为 false → 所有菜单被过滤掉 → 侧边栏空。

**解决方法**：改 `m.parentId === 0` 为 `+m.parentId === 0`（一元 `+` 转数字），同时去掉 `m.visible === 1` 的过滤（后端根本没返回 `visible` 字段）。

**你的想法**：


**我的想法**：Jackson 全局 Long→String 是个全局决策，影响了每一个返回的 Long 字段。前端任何 `===` 数字的比较都会静默失败。正确的做法是：要么统一在 axios 拦截器里做类型还原，要么所有前端比较都用 `==` 或显式转换。宁可多写几个 `+`，也不要相信后端返回的数字类型。

### 14. CORS 跨域 — Sa-Token 拦截了 OPTIONS 预检请求

**类别**：后端 - 中间件配置

**现象**：前端换到端口 5174 后，Dashboard 所有接口全部被浏览器拦截，Console 刷屏 CORS policy 错误。

**原因**：浏览器跨域时先发 OPTIONS 预检请求。Sa-Token 的 `SaInterceptor` 拦截了 `/api/**` 所有请求，OPTIONS 不带 token，被 `checkLogin()` 踢回 401。浏览器收到非 2xx 的预检响应 → 判定跨域失败 → 拦截所有后续 GET/POST 请求。

**解决方法**：在 `SaInterceptor` 的 lambda 里，通过 `RequestContextHolder` 获取当前请求，判断 `"OPTIONS".equalsIgnoreCase(req.getMethod())`，是则跳过 `checkLogin()`。

**你的想法**：


**我的想法**：这是一个经典的中间件顺序问题。CORS 预检是浏览器层面的安全机制，应该在业务拦截器之前处理。Spring 的 `CorsFilter` 默认在拦截器链之前，但 Sa-Token 的 `SaInterceptor` 是手动注册的，它会抢在 CORS 处理之前执行。教训：给任何 `/api/**` 全局拦截器加逻辑时，第一件事就是放行 OPTIONS。

### 15. ECharts 图表不显示 — DOM 容器初始化时宽高为 0

**类别**：前端 - 图表渲染

**现象**：Dashboard 的饼图和柱状图不显示，Console 刷屏 `Can't get DOM width or height`。

**原因**：`onMounted` 里 `await` 数据加载完后立即调 `echarts.init()`。但此时 CSS Grid 布局还没算完，图表容器 `div` 的 `clientWidth` 为 0，ECharts 无法确定画布大小。

**解决方法**：`await nextTick()` 等 Vue DOM 更新 + 布局计算完成后再初始化图表；加 `el.clientWidth === 0` 的防御检查；复用图表实例（dispose 旧的再 init 新的）防止重复 mount。

**你的想法**：


**我的想法**：`onMounted` 只保证 DOM 节点已插入文档，不保证 CSS 布局已计算。任何依赖 `clientWidth`/`clientHeight` 的第三方库（ECharts、Canvas、D3），都应该包在 `nextTick` 或 `requestAnimationFrame` 里初始化。

### 16. `menus.value` 为 null 导致 `.filter()` 崩溃

**类别**：前端 - 异常处理

**现象**：`Cannot read properties of undefined (reading 'filter')` 在 `MainLayout.vue` 菜单计算属性里报了两次。

**原因**：`safeJSON` 函数里 `JSON.parse("null")` 合法返回 JavaScript 的 `null`，但接着直接 `return raw ? JSON.parse(raw) : fallback` 把 `null` 当有效值返回了。`menus.value` 变成 `null`，`.filter()` 炸了。

**解决方法**：`safeJSON` 改为 `const v = raw ? JSON.parse(raw) : null; return v != null ? v : fallback`；同时 `menuTree` 计算属性里加 `const list = menus.value || []` 双重保险。

**你的想法**：


**我的想法**：`JSON.parse("null")` 是合法的，返回 `null` 不是错误。安全解析函数的"安全"要同时覆盖"解析异常"和"解析出 null/undefined"。用 `!= null` 判断（匹配 null 和 undefined）是最简洁的写法。

### 17. views 目录按业务模块分，不按角色分

**类别**：前端 - 项目结构

**现象**：`views/` 下面是 `org/`、`exam/`、`risk/`、`system/` 等业务模块目录。项目有 4 种角色（admin / hr / 主管 / 员工），但打开目录看不出谁有权访问什么。

**原因**：初始设计按业务领域划分子目录，这是后台管理系统的标准做法。但对于一个"毕设需要答辩演示"的项目，评委看到文件夹结构不知道权限边界，得翻路由代码才能理解。

**解决方法**：不改变 URL 路径，只改文件组织结构（最终改为按角色分路径 `/admin/*`、`/hr/*`、`/leader/*`、`/my/*`）。

**你的想法**：


**我的想法**：按业务模块分和按角色分各有适用场景。大项目（几十个页面、多团队协作）应该按业务模块分。毕设这种 20 页以内的小项目，按角色分让非技术人员也能快速理解系统设计。最终进一步把 URL 也按角色分隔，参考了星河健康的做法。

### 18. 代码风格落后于 2026 年标准

**类别**：后端 - 代码风格

**现象**：Entity 手写 getter/setter（58 行一个 User 类）、DTO 用普通 class、Service 用 `import java.util.*` 通配符。

**原因**：项目 pom.xml 引了 Lombok 但没用；Java 17 支持 Record 但没用；IDE 默认用了通配符导入。

**解决方法**：
- 19 个 Entity 统一加 `@Getter @Setter`，代码量减半
- 5 个 DTO 改为 Java Record（`UserImportDTO` 保留，EasyExcel 需要 setter）
- 15 个 Service 的通配符导入全部改为具体导入

**你的想法**：


**我的想法**：Lombok 和 Record 不是追求"新"，而是减少样板代码。一个 User 类从 58 行变成 31 行，少写的 27 行就是少 27 个潜在的拼写错误。Record 比 class 更适合 DTO —— 不可变、自动生成 equals/hashCode/toString，一行代码搞定以前 10 行的事。

### 19. 侧边栏空白 — 动态菜单渲染失败（两次）

**类别**：前端 - 渲染逻辑

**现象**：admin 登录后侧边栏一片空白，Dashboard 内容能显示。

**原因**：翻了两次。

**第一次**：后端 `buildMenuTree()` 返回的数据已经嵌套了 `children`（`[{id:"1", children:[...]}]`），但前端又用 `list.filter(m => m.parentId === dir.id)` 从 flat 列表匹配 children，结果永远找不到（因为 children 已嵌套在对象内部），覆盖成了 `null`。`el-sub-menu v-if="dir.children"` 判断失败，无菜单项渲染。

修法：删掉 `.map()` 里的 children 匹配逻辑，直接用 API 原样数据。

**第二次**：修了以上 bug 后侧边栏依然空。对比 `E:/Claude/Galaxy Health` 项目的写法，发现根本性问题——不能依赖动态菜单渲染。

**根本原因**：从后端 API 动态读取菜单数据来渲染侧边栏，链路太长（登录 → token → /api/auth/me → menus JSON → localStorage → store → computed → el-menu 渲染），中间任何一环出问题侧边栏就空。后端 RBAC 已经通过 `@SaCheckPermission` 保护了 API 层，前端侧边栏没必要再动态化。

**解决方法**：
- 侧边栏菜单**硬编码**到 AdminLayout.vue 模板里，不读 API 数据
- 用 Element Plus `el-container`/`el-aside`/`el-main` 标准布局
- CSS 用 `:deep()` 穿透而不是 `scoped` 嵌套选择器
- 参考星河健康 `admin/AdminLayout.vue` 的写法

**你的想法**：


**我的想法**：动态菜单渲染在理论上更灵活（admin 可以在后台改菜单），但实际上菜单结构一旦定下来就不会频繁变动。用动态渲染增加了复杂度和 bug 概率，换来的灵活性在这个项目规模下不值得。后端权限控制才是真正的安全边界，前端菜单只是导航，硬编码完全可以。

### 20. 侧边栏跳转延迟 — `<transition mode="out-in">` 人为制造空白

**类别**：前端 - 用户体验

**现象**：点击侧边栏菜单项，页面跳转有明显延迟（约 0.5 秒空白），感觉"卡"。

**原因**：三个 Layout 组件里 `<router-view>` 包了 `<transition name="fade" mode="out-in">`。`mode="out-in"` 的机制是先等旧页面完全淡出（250ms），再开始新页面淡入（250ms）。加起来约 0.5 秒的空白期，用户感知为"卡顿"。

**解决方法**：去掉 `<transition>` 包裹，直接用 `<router-view />`。Vue Router 本身切换是瞬间的，不需要动画。

**你的想法**：


**我的想法**：页面过渡动画在 C 端产品里能提升质感，但在后台管理系统里是负优化。后台用户追求的是操作效率，每次点击等半秒累计起来就是糟糕的体验。如果一定要动画，至少去掉 `mode="out-in"`，让新旧页面同时替换。

### 21. 数据权限越权 — 单条详情接口无校验

**类别**：后端 - 权限漏洞

**现象**：员工 emp01 登录后，访问 `GET /api/records/{id}` 传入任意 recordId，能看到其他员工的体检明细；`GET /api/rag/health-advice?recordId=` 同理能拿到别人的异常指标和 AI 建议。

**原因**：列表查询都走了 DataScopeUtil，但**按 id 查单条的 `detail()` 方法没有做任何权限校验**。RagController 直接查 exam_result_item 表也没校验。

**解决方法**：
- `ExamRecordServiceImpl.detail()` 加 `checkViewPermission(record)`：scope=0 全量、scope=1 只能看本部门、scope=2 只能看自己
- `RagController.healthAdvice()` 加同样校验
- `RagController.suggestPlan()` 加 `@SaCheckPermission("risk:assess")`（管理端功能，之前无权限注解）

**你的想法**：

**我的想法**：数据权限最常见的遗漏点不是列表查询，而是"按 id 查详情"这类单条接口——开发者容易默认"能查到 id 就有权限"。审计时要专门盯 `@PathVariable`/`@RequestParam id` 的接口。

### 22. 登录日志从未写入

**类别**：后端 - 半成品功能

**现象**：`login_log` 表一直为空，登录日志页面查不到任何记录。

**你的想法**：

**我的想法**：功能文档里写"待实现"就要在交付前补完。登录日志是审计刚需，答辩时页面是空的会很难看。这种"表结构+查询都好了、只差写入"的半成品是最容易补的，成本也最低。

### 23. RAG 模型名写死导致 model_not_found

**类别**：后端 - 配置不一致

**现象**：调用 suggest-plan 返回 500，日志显示 `The model deepseek-chat does not exist`。

**你的想法**：

**我的想法**：配置写死在代码里和写在 yml 里不一致，是最典型的环境问题。模型名这种随平台变化的东西，永远应该走配置。
